# Доставка (Delivery)

## Назначение
Довести проверенный код до дев-стенда через существующий git/CI-процесс
проекта. Эта стадия НЕ хранит и не использует секреты деплоя напрямую —
она только инициирует уже настроенный в проекте pipeline.

## Предусловие
`fe-quality-gate` должен вернуть полностью зелёный отчёт. Если есть
незакрытые провалы проверок — остановись и верни пользователя к
предыдущей стадии.

## Инструкции

1. **Определи git-конвенции проекта**:
   - Формат сообщений коммитов (conventional commits `feat:`/`fix:`/`chore:`
     или иной, принятый в проекте — проверь историю `git log`).
   - Схему именования веток (например, `feature/{TICKET}-{краткое-описание}`).

2. **Создай ветку и закоммить изменения**:
   ```
   git checkout -b feature/{TICKET}-{краткое-описание}
   git add {изменённые файлы}
   git commit -m "{тип}({область}): {краткое описание на русском или в стиле проекта}"
   ```

3. **Сформируй Pull Request** по шаблону `templates/pr-template.md`,
   включающий:
   - Краткое описание сделанного.
   - Ссылку на исходную постановку (тикет/ФТТ).
   - Список открытых некритичных вопросов из `spec.md` (если остались).
   - Чек-лист выполненных проверок из отчёта `fe-quality-gate`.

4. **Отправь ветку и открой PR** через доступный инструмент (git CLI +
   доступ к репозиторию, либо через уже настроенный в среде MCP-коннектор
   к GitHub/GitLab, если он подключён). Не пытайся напрямую взаимодействовать
   с секретами CI/CD — только с git и API репозитория.

5. **Дождись/проверь срабатывание существующего CI/CD** пайплайна проекта
   (не создавай новый pipeline с нуля, если он уже есть).

6. **Выполни smoke-check дев-стенда** после деплоя: запрос по URL дев-стенда,
   проверка кода ответа (200) и базовой доступности изменённого раздела.

7. Сформируй финальный отчёт (`handoff-report.md`): что сделано, ссылка на
   PR, ссылка на дев-стенд, статус smoke-check, оставшиеся открытые вопросы
   для бизнес-аналитика/тимлида.

## Формат вывода
Открытый PR + результат smoke-check + файл `handoff-report.md`.
