# Реализация (Implementation)

## Назначение
Написать код строго на основе `spec.md`, `design-plan.md` и `adr.md` —
не изобретая архитектуру заново на этом шаге.

## Предусловие
Должны существовать все три предыдущих артефакта. Если `adr.md` отсутствует
или в нём есть незакрытые противоречия — верни пользователя к предыдущей
стадии.

## Инструкции

1. **Прочитай `adr.md` и следуй ему буквально** — пути файлов, выбранная
   технология состояния, паттерны обработки ошибок должны совпадать с тем,
   что там зафиксировано.

2. **Перед написанием каждого файла проверь конвенции репозитория**:
   - Стиль импортов, порядок пропсов, naming (camelCase/PascalCase),
     стилизация (CSS Modules/styled-components/Tailwind — используй то, что
     уже принято в проекте).
   - Не вводи новую библиотеку, которой нет в `package.json`, без явного
     согласования с пользователем.

3. **Покрой ВСЕ состояния из `spec.md`** явно в коде — загрузка, пусто,
   успех, ошибка, частичные данные. Отсутствие обработки любого из
   зафиксированных состояний — дефект этой стадии.

4. **Заложи доступность (a11y)** по умолчанию:
   - Семантические теги, `aria-*` атрибуты для интерактивных элементов.
   - Управление фокусом при модальных окнах/динамическом контенте.
   - Проверка контраста не выполняется кодом, но если UI-kit предоставляет
     token для контраста — используй его, а не произвольные цвета.

5. **Типизация**: строгие типы для пропсов и данных (TypeScript), без `any`,
   если в проекте включён strict mode.

6. **Не пиши тесты на этом шаге** — это ответственность стадии
   `fe-quality-gate`. Реализация должна быть тестируемой (например, доступной
   через роли/aria, а не только через классы/testid, если это не принято в
   проекте).

7. По завершении выведи список созданных/изменённых файлов и краткое резюме,
   какие решения из ADR были применены.

## Формат вывода
Изменённые/созданные файлы кода в путях, зафиксированных в `adr.md`, плюс
короткое текстовое резюме для пользователя.
