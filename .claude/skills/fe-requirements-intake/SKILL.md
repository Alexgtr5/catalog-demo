# Разбор требований (Requirements Intake)

## Назначение
Это первая стадия пайплайна фронтенд-разработки. Задача — превратить свободный текст
постановки (ФТТ, пользовательский путь) в строгую, проверяемую спецификацию, на
основе которой можно безопасно проектировать UX и архитектуру. Стадия обязана
останавливать процесс при обнаружении критических пробелов, а не додумывать их.

## Когда НЕ применять
Не используй этот skill, если пользователь уже предоставил готовую структурированную
спецификацию (например, файл spec.md от предыдущего запуска) — в этом случае сразу
переходи к стадии `fe-ux-scaffolding`.

## Инструкции

1. **Прочитай исходный текст требования полностью**, включая все приложенные
   пользовательские сценарии/флоу.

2. **Определи тип задачи** по объёму: страница целиком / виджет / отдельный
   UI-kit компонент. От этого зависит глубина следующих стадий (см. раздел
   "Масштабирование" ниже) — зафиксируй это явно в начале spec.md.

3. **Извлеки структурированные данные**:
   - **Сущности** — объекты предметной области, участвующие в задаче (например,
     "Товар", "Пользователь", "Список избранного").
   - **Пользовательские действия** — конкретные глаголы: добавить, удалить,
     отфильтровать, отправить, отменить и т.д. Для каждого действия отметь
     триггер (откуда вызывается) и результат.
   - **Состояния экрана/компонента** — обязательно пройдись по чек-листу:
     - загрузка (loading)
     - пусто (empty)
     - успех (success)
     - ошибка (error)
     - частичные/неполные данные (partial)
     Если постановка не описывает какое-то из состояний — это открытый вопрос,
     а не повод придумать поведение самому.
   - **Технические ограничения** — персистентность данных, авторизация,
     ограничения по устройствам/браузерам, производительность, если упомянуты.
   - **Интеграции** — какие API/бэкенд-эндпоинты нужны. Если контракт API не
     описан явно (URL, метод, формат ответа) — это ВСЕГДА открытый вопрос,
     закрывающий переход к реализации.

4. **Сформируй файл `spec.md`** по шаблону `templates/spec-template.md` в этой
   же директории skill'а.

5. **Заполни раздел "Открытые вопросы"** для всего, что явно не указано в
   постановке, но необходимо для реализации. Формулируй вопрос конкретно,
   не общими словами ("что делать при ошибке?" — плохо; "какой текст и UI
   показывать при ошибке 500 от /api/favorites — toast, inline-сообщение или
   полноэкранный error state?" — хорошо).

6. **Правило блокировки**: если в разделе "Открытые вопросы" есть хотя бы один
   пункт, помеченный как **критичный** (блокирует безопасную реализацию —
   обычно это отсутствие API-контракта или неоднозначность ключевого сценария),
   явно сообщи об этом пользователю и НЕ переходи к следующей стадии
   автоматически. Некритичные вопросы (например, "нет лимита на количество
   элементов") можно пометить как "не блокирует, уточнить позже" и продолжить.

7. Не придумывай данные, которых нет в постановке. Если нужно предположение —
   помечай его явно как "Предположение:" с обоснованием, а не выдавай за факт.

## Формат вывода
Файл `spec.md` (см. шаблон). Ответ пользователю — краткое резюме: тип задачи,
сколько состояний экрана определено, список критичных открытых вопросов (если
есть) с явной пометкой "требуется подтверждение перед продолжением".

## Масштабирование по типу задачи
- **Страница** — полный разбор по всем пунктам выше.
- **Виджет** — то же самое, но без раздела "навигация/маршрутизация", если
  виджет не меняет URL/роутинг.
- **UI-kit компонент** — пользовательский путь часто отсутствует; вместо него
  разбираются props/варианты компонента (variants, sizes, states) и контракт
  использования (кто и как будет его переиспользовать).

## Пример
См. `templates/spec-template.md` и разобранный кейс в общей документации
пайплайна (виджет "Избранное").
