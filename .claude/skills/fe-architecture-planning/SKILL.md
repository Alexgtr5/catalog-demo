# Архитектурное планирование (Architecture Planning)

## Назначение
Принять и зафиксировать технические решения до написания кода, строго в
соответствии с конвенциями существующего репозитория — а не по личным
предпочтениям исполнителя.

## Предусловие
Должны существовать `spec.md` и `design-plan.md` от предыдущих стадий.

## Инструкции

1. **Просканируй репозиторий перед любыми решениями**:
   - Структура папок в `src/` — определи используемую конвенцию (Feature-Sliced
     Design, Atomic Design в коде, кастомная структура по фичам/доменам).
   - Как в проекте уже реализовано управление состоянием для похожих задач
     (Redux/Zustand/Context/React Query/SWR/локальный state) — ищи прецеденты,
     не предлагай технологию, которой ещё нет в проекте, без явного обоснования.
   - Как оформлены похожие фичи (naming, паттерны хуков, работа с формами).
   - Как в проекте обрабатываются ошибки и уведомления (есть ли общий
     toast/notification механизм).

2. **Прими решения по каждому пункту** и обязательно обоснуй, опираясь на
   найденные прецеденты в репозитории, а не на общие best practices "вообще":
   - Управление состоянием (локальное/серверное/глобальное).
   - Стратегия получения данных (когда грузим, кэшируем, инвалидируем).
   - Расположение новых файлов (конкретные пути).
   - Обработка ошибок и edge cases из spec.md (что происходит при каждом
     состоянии "ошибка"/"частичные данные").
   - Что из design-plan.md требует нового примитива в UI-kit — как это
     реализуется (в общем UI-kit или локально для задачи).

3. **Зафиксируй отклонённые альтернативы** — какие подходы рассматривались и
   почему не выбраны. Это обязательный раздел, не опциональный.

4. Сформируй `adr.md` по шаблону `templates/adr-template.md`.

5. Если в ходе сканирования репозитория обнаружено противоречие с spec.md
   или design-plan.md (например, дизайн-план предполагает компонент, для
   которого в репозитории уже есть другой похожий, но иначе называющийся) —
   останови процесс и сообщи пользователю вместо тихого решения самому.

## Формат вывода
Файл `adr.md`: контекст, принятые решения с обоснованием, отклонённые
альтернативы, точные пути файлов для стадии реализации.
