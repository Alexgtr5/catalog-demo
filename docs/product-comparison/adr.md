# ADR: Виджет «Сравнение товаров» — архитектурные решения

## Контекст

Исходные документы — `docs/product-comparison/spec.md` (все критичные вопросы
закрыты) и `docs/product-comparison/design-plan.md` (дерево компонентов на
существующем UI-kit).

Задача: список до 3 товаров, таблица характеристик по столбцам, объединение
характеристик с прочерком, персистентность в `sessionStorage`, уведомление о
лимите, кнопка-переключатель на карточке товара.

Сканирование репозитория дало четыре прецедента, на которые опираются решения:

- **Расшаривание состояния между несвязанными компонентами** —
  `src/shared/ui/toastContext.ts` + `ToastProvider.tsx` + `useToast.ts`:
  контекст, провайдер и хук лежат в трёх отдельных файлах.
- **Чистая логика отдельно от компонентов** —
  `src/features/filter-products/model/filterProducts.ts`: чистая функция в
  `model/`, покрытая юнит-тестами отдельно от UI.
- **Загрузка данных** — `src/entities/product/model/useProducts.ts`:
  `useState` + `useEffect`, без библиотек. React Query, Redux, Zustand в
  проекте отсутствуют (зависимости — только `react` и `react-dom`).
- **Публичный API слайса** — у каждого слайса есть `index.ts`, наружу
  экспортируется только он.

## Решения

### Управление состоянием

**Выбор: React Context + `useState`, вся логика изменений — в чистых функциях.**

Данные списка сравнения клиентские (максимум три строковых id), серверной
синхронизации нет, но состояние нужно одновременно карточкам товаров и виджету
таблицы. Это ровно тот случай, который в проекте уже решён через Context —
`ToastProvider` расшаривает `showToast` между произвольными компонентами.
Повторяем этот паттерн, включая разделение на три файла (контекст, провайдер,
хук), которое в проекте сделано ради корректной работы Fast Refresh и правил
линтера.

`useReducer` не используется: в репозитории нет ни одного прецедента, а вся
нетривиальная логика (проверка лимита, переключение) выносится в чистые функции
по образцу `filterProducts` — их проще тестировать изолированно, чем поведение
редьюсера.

### Стратегия получения данных: подъём загрузки на уровень страницы

**Выбор: `useProducts` вызывается в `CatalogPage`, товары передаются пропсами в
`CatalogGrid` и `ComparisonWidget`.**

Это следствие находки при сканировании: сейчас `useProducts()` вызывается внутри
`CatalogGrid` (`src/widgets/catalog/ui/CatalogGrid.tsx:10`) и больше нигде.
Виджету сравнения нужны те же товары — он хранит только id, а разворачивает их в
полные объекты. Если бы он вызвал `useProducts` самостоятельно, приложение
выполнило бы **две независимые загрузки** каталога с двумя независимыми
состояниями: таблица сравнения могла бы показывать скелетон, когда сетка товаров
уже отрисована, и наоборот.

**Последствие для существующего кода, которое нужно учесть на стадии
реализации:** контракт `CatalogGrid` меняется — компонент перестаёт грузить
данные сам и начинает принимать `products`, `status`, `reload` пропсами.
Существующие тесты `src/widgets/catalog/ui/CatalogGrid.test.tsx` рендерят
`<CatalogGrid />` без пропсов и потребуют обновления. Это не побочный
рефакторинг, а необходимое условие непротиворечивости состояний загрузки.

### Расположение в кодовой базе

```
src/entities/comparison/
├── model/
│   ├── comparisonContext.ts       контекст (по образцу toastContext.ts)
│   ├── ComparisonProvider.tsx     состояние + синхронизация с sessionStorage
│   ├── useComparison.ts           хук доступа к контексту
│   ├── toggleComparison.ts        чистая логика переключения и лимита
│   ├── comparisonStorage.ts       чтение/запись sessionStorage
│   └── buildComparisonRows.ts     построение строк таблицы
└── index.ts                       публичный API слайса

src/features/toggle-comparison/
├── ui/ToggleComparisonButton.tsx  кнопка в слот footer у ProductCard
└── index.ts

src/widgets/comparison/
├── ui/ComparisonWidget.tsx        выбор состояния: скелетон / пусто / таблица
├── ui/ComparisonTable.tsx         таблица со залипающей первой колонкой
├── ui/ComparisonTable.module.css
├── ui/ComparisonTableSkeleton.tsx композиция <Skeleton>
└── index.ts
```

`ComparisonProvider` подключается в `src/app/App.tsx` рядом с `ToastProvider` —
там уже собираются провайдеры приложения.

Слой `entities` выбран потому, что список сравнения — предметная сущность из
`spec.md`, а не пользовательское действие; сами действия (кнопка-переключатель)
живут в `features`, как и `filter-products`.

### Обработка ошибок и edge cases

- **Загрузка каталога** → `ComparisonWidget` показывает `ComparisonTableSkeleton`
  (решение №2 из spec.md). Статус берётся из того же источника, что и у сетки
  товаров, поэтому рассинхронизации не возникает.
- **Ошибка загрузки каталога** → виджет не рендерится вовсе; сообщение об ошибке
  показывает `CatalogGrid`, как и сейчас. Дублирования сообщений не будет.
- **Неизвестный id в хранилище** → отбрасывается при развёртывании id в товары
  (`useMemo` в виджете). **Хранилище при этом не очищается**: каталог может быть
  временно недоступен, и стирать выбор пользователя из-за сетевой ошибки нельзя.
  Как только товар снова появится в выдаче, столбец вернётся.
- **Повреждённые данные в `sessionStorage`** → чтение обёрнуто в `try/catch`,
  при ошибке разбора возвращается пустой список. Это граница системы (внешнее
  хранилище), поэтому валидация здесь оправдана. Дополнительно список
  обрезается до лимита: в хранилище могло оказаться больше трёх id.
- **Достижение лимита** → `toggleComparison` возвращает
  `{ ids, limitReached }`; состав списка не меняется, кнопка показывает toast с
  `variant="warning"`. Проверка лимита живёт в чистой функции, а не в компоненте,
  поэтому её нельзя обойти из другого места UI.
- **Удаление товара из таблицы и с карточки** — одно и то же действие над одним
  состоянием; набор строк пересчитывается, так как часть характеристик могла
  принадлежать только удалённому товару.

### Новые примитивы UI-kit

Три риска из `design-plan.md` решаются по-разному — намеренно, а не единообразно.

1. **Таблица с залипающей первой колонкой → локально в виджете, в UI-kit не
   выносится.** Потребитель ровно один; общий табличный примитив без второго
   сценария спроектировать правильно невозможно. Реализация — `position: sticky`
   на первой колонке внутри `ComparisonTable.module.css`.

2. **Дубликаты `Toast` → правка общего `ToastProvider`.** Единственное изменение
   UI-kit в этой задаче. Обоснование: стопка одинаковых уведомлений — дефект
   самого примитива, воспроизводимый в любом сценарии с быстрыми повторными
   вызовами, а не особенность сравнения товаров. `showToast` не добавляет
   уведомление, если сообщение с тем же текстом уже отображается. Изменение
   обратно совместимо: публичная сигнатура `showToast` не меняется.

3. **Жёсткие отступы `EmptyState` → оставляем как есть.** Компонент используется
   без изменений. Макетов нет, поэтому «заглушка занимает много места» —
   предположение, а не подтверждённый дефект. Добавлять проп размера в общий
   примитив ради невыверенного визуального ощущения преждевременно; вернуться к
   вопросу, когда появится дизайн.

## Отклонённые варианты

- **`useReducer` с действием `LIMIT_REACHED`** — отклонён: в репозитории нет
  прецедента использования редьюсеров, а чистые функции в `model/` (как
  `filterProducts`) дают ту же централизацию логики и тестируются проще.
- **Redux / Zustand** — отклонён: избыточно для трёх строковых id, потребовал бы
  новой зависимости в проекте, где сейчас только `react` и `react-dom`.
- **React Query** — отклонён: данные клиентские, кэш и инвалидация не нужны;
  библиотеки в проекте нет.
- **`localStorage`** — отклонён: дал бы персистентность между сессиями, что прямо
  противоречит постановке.
- **Собственный вызов `useProducts` внутри виджета сравнения** — отклонён:
  приводит к двум независимым загрузкам каталога и рассинхронизации состояний
  загрузки между сеткой и таблицей.
- **Кэш промиса в `productsApi`** (модуль-синглтон, чтобы оба потребителя
  получали одни данные) — отклонён: вводит скрытое глобальное состояние в слой
  api, ломает предсказуемость тестов и маскирует проблему вместо того, чтобы
  решить её композицией.
- **Блокировать кнопку (`disabled`) у товаров вне сравнения при заполненном
  лимите** — отклонён: постановка требует уведомления при попытке добавить
  четвёртый товар, а у заблокированной кнопки события клика не возникает.
- **Хранить в `sessionStorage` полные объекты товаров** вместо id — отклонён:
  данные каталога дублировались бы и устаревали; id плюс развёртывание из
  загруженного каталога решает это без рассинхронизации.

## Точки входа для стадии реализации

1. `src/entities/comparison/**` — новый слайс целиком.
2. `src/features/toggle-comparison/**` — новый слайс.
3. `src/widgets/comparison/**` — новый слайс.
4. `src/app/App.tsx` — подключение `ComparisonProvider`.
5. `src/pages/catalog/CatalogPage.tsx` — подъём `useProducts`, размещение виджета
   над сеткой.
6. `src/widgets/catalog/ui/CatalogGrid.tsx` — приём данных пропсами, передача
   кнопки в слот `footer` у `ProductCard`.
7. `src/widgets/catalog/ui/CatalogGrid.test.tsx` — обновление под новый контракт.
8. `src/shared/ui/ToastProvider.tsx` — подавление дубликатов.
